<a id="d-01"></a>
## D-01 🟠 `sum_prop_pair`: der Fallback widerspricht dem echten Default

*(Das ist der Punkt, den ich gestern unklar formuliert hatte.)*

### Was ist das Problem

`sum_prop_pair` schaltet um, aus welcher Propensity der Zeitschritt berechnet
wird — aus der **vor** dem Ereignis, oder aus dem logarithmischen Mittel von
vorher und nachher. Zwei verschiedene Zeitschritt-Verfahren.

Der Schalter wird an **einer** Stelle gesetzt:

```python
# mcpbe_base.py:224, in MCPBEBase.__init__
self.sum_prop_pair = False
```

Gelesen wird er an **drei** Stellen, überall so:

```python
# mcpbe_time_helper.py, in allen drei _build_*_dt_strategy
use_pair = bool(getattr(self, "sum_prop_pair", True))
#                                              ^^^^ Fallback: True
```

Der zweite Parameter von `getattr` greift nur, wenn das Attribut **fehlt**. Er
sagt also: „falls niemand `sum_prop_pair` gesetzt hat, nimm `True`" — während
der tatsächlich gesetzte Wert `False` ist. Die beiden widersprechen sich.

### Warum ist es ein Problem

Heute passiert nichts: `__init__` setzt das Attribut immer, der Fallback greift
nie. Das Problem ist die Falle für später. Sobald das Attribut einmal fehlt,
rechnet der Solver **stillschweigend nach dem anderen Verfahren** — keine
Exception, keine Warnung, nur andere Zahlen. Wege dahin:

- `MCPBETimeHelper` wird in eine Klasse gemischt, deren `__init__` das nicht setzt
- `__init__` wird umgebaut und die Zeile rutscht hinter einen `return`/`if`
- ein Objekt entsteht ohne `__init__` (Unpickling, Test-Dummy, `__new__`)

Genau die Klasse von Fehler, die bei einem Monte-Carlo-Solver teuer ist: das
Ergebnis ist plausibel, nur eben anders — und niemand weiß, warum ein alter Lauf
sich nicht reproduzieren lässt.

Dazu kommt: wer die drei Zeilen liest, hält `True` für den Default. Ich bin
beim Dokumentieren selbst darauf reingefallen und musste in `mcpbe_base.py`
nachsehen.

### Wie könnte man das Problem lösen

Drei Möglichkeiten, in meiner Reihenfolge:

1. **Fallback angleichen** — `getattr(self, "sum_prop_pair", False)` an allen
   drei Stellen. Kleinste Änderung, kein Verhaltensunterschied im Normalbetrieb.
2. **Klassenattribut statt getattr** — `sum_prop_pair: bool = False` als
   Klassenvariable auf `MCPBETimeHelper`, dann `if self.sum_prop_pair:`. Der
   Default steht damit dort, wo der Schalter gelesen wird, und `__init__` darf
   ihn weiterhin überschreiben. Räumt die Frage dauerhaft ab.
3. **Laut scheitern** — kein Fallback, `self.sum_prop_pair` direkt lesen. Fehlt
   das Attribut, gibt es einen `AttributeError` statt stiller Verhaltensänderung.

Dasselbe gilt für `exp_time_step` (`getattr(self, "exp_time_step", False)`) —
dort stimmt der Fallback allerdings mit dem gesetzten Wert überein.

### Entscheidung (21.08.2026)

**Option 1 umgesetzt** — Fallback an allen drei Stellen auf `False` angeglichen.
Kein Verhaltensunterschied im Normalbetrieb; Import- und Referenzlauf danach
geprüft.

## D-02 🟠 Sprachmix innerhalb einzelner Dateien

### Was ist das Problem

Nicht „manche Datei deutsch, manche englisch" — es kippt **innerhalb** derselben
Datei. `helpers.py`:

```python
"""
WMCPBE Helper Functions & Config Templates.        ← Modul-Docstring: Englisch
This module provides convenience functions and ...
"""

def setup_initial_particles(...):
    """
    Initialisiert Partikelarrays für Solver.       ← Funktion darunter: Deutsch
    ...
    Parameter                                      ← deutscher Section-Header
    ---------
```

Betroffen: `helpers.py`, `kernels/base.py`, `mcpbe_agg.py`. Deutsche
Section-Header (`Parameter`, `Rückgabe`) gibt es **57×**, davon 23 in `wmcpbe`
und 34 im älteren `src/mcpbe`.

### Warum ist es ein Problem

Zwei getrennte Effekte:

- **Lesbarkeit.** Wer die Datei von oben liest, wechselt mitten im File die
  Sprache. Für eine KI, die Kontext aus dem Modul-Docstring zieht und dann auf
  deutsche Parameterbeschreibungen trifft, ist es dasselbe Problem.
- **Werkzeuge.** Sphinx/napoleon kennt nur `Parameters` und `Returns`. Die
  deutschen Varianten werden nicht als Parameterliste erkannt, sondern als
  Fließtext durchgereicht — die Tabelle fehlt in der generierten Doku
  ersatzlos. Praktisch fällt das heute nicht auf, weil der Sphinx-Build
  ohnehin nicht läuft (siehe [D-07](#d-07)).

### Wie könnte man das Problem lösen

Deine bereits getroffene Entscheidung durchziehen: **Code durchgehend Englisch,
README und `docs/` Deutsch.** Konkret im Durchgang:

- deutsche Docstrings übersetzen, dabei nach der neuen Kürze-Regel gleich mit
  eindampfen
- `Parameter` → `Parameters`, `Rückgabe` → `Returns`, `Hinweise` → `Notes`
- `src/mcpbe` mitnehmen oder bewusst auslassen — dort liegen 34 der 57 Header,
  und das Paket ist der ältere Solver (siehe auch [D-13](#d-13))

## D-04 🟡 Fünf Dateien mit UTF-8-BOM

### Was ist das Problem

```
mcpbe/src/wmcpbe/__init__.py
mcpbe/src/wmcpbe/lmc_adapter.py
mcpbe/src/wmcpbe/mcpbe.py
mcpbe/src/wmcpbe/mcpbe_break.py
mcpbe/src/wmcpbe/reconstruction_mixin.py
```

Drei unsichtbare Bytes (`EF BB BF`) vor dem ersten Zeichen. In `src/mcpbe`
kommen 12 weitere dazu. Stammt typischerweise davon, dass eine Datei einmal
mit dem Windows-Editor oder PowerShell `Out-File` gespeichert wurde.

### Warum ist es ein Problem

Python 3 verträgt das, es ist also kein akuter Fehler. Aber: `git diff` zeigt
die erste Zeile als geändert an, wenn jemand die Datei mit einem BOM-freien
Editor speichert; Werkzeuge, die Dateien zeilenweise einlesen, sehen in Zeile 1
ein Zeichen mehr als erwartet; und ein Modul-Docstring, der nach einem BOM
beginnt, wird von manchen Parsern nicht als solcher erkannt.

Da ich ohnehin jede dieser Dateien anfasse, kostet das Entfernen nichts.

### Wie könnte man das Problem lösen

Beim Schreiben der dokumentierten Fassung ohne BOM speichern. Ich kann es als
Prüfschritt am Ende des Durchgangs mitlaufen lassen.

## D-05 🟡 73 Zeilen Docstring für 12 Zeilen Code

### Was ist das Problem

`mcpbe.py::create_nucleation_handler` hat eine Docstring von **73 Zeilen** vor
einem Methodenkörper von 12. Darin erklärt: was Computational Weight ist, was
`n_comp` gegen `n_phys` ist, wie die DSMC-Skalierung funktioniert, zwei
Zahlenbeispiele. Dieselben Konzepte stehen außerdem in der Klassen-Docstring
direkt darüber, in `.agents/informations.txt` und in `Fundamentals.md`.

Dazu in derselben Datei zweimal:

```python
def create_nucleation_handler(self, **kwargs):
    """..."""
    import warnings          # ← Zeile 125, und nochmal Zeile 190
```

### Warum ist es ein Problem

- **Redundanz.** Vier Kopien derselben Erklärung. Ändert sich das Verständnis,
  müssen vier Stellen nach — realistisch geht eine vergessen, und dann
  widersprechen sich die Dokumente.
- **Signal-Rausch.** Was diese Methode *tut* (Handler bauen, bei
  Doppelaufruf warnen) geht zwischen den Grundlagen unter.
- Der `import` im Methodenkörper hat keinen erkennbaren Grund — `warnings` ist
  Standardbibliothek, kein schwerer oder zirkulärer Import.

### Wie könnte man das Problem lösen

Der Kern deiner Devise: Konzepte genau **einmal**, nämlich in der neuen README.
Die Docstring behält, was nur hier gilt — die beiden Wege, die Dauer anzugeben,
und die Konsistenzprüfung. Verweis auf die README statt Wiederholung. Grobe
Schätzung: 73 → ~15 Zeilen. Die beiden `import warnings` nach oben.

## D-07 🔴 Der CI-Workflow für die Doku kann nicht durchlaufen

### Was ist das Problem

`.github/workflows/docs.yml` baut die Sphinx-Doku und deployt sie nach GitHub
Pages. Zwei Schritte darin passen nicht mehr zum Repo:

```yaml
- run: pip install -e .                              # es gibt kein Root-pyproject.toml
- run: sphinx-apidoc -o docs/api -e -M -f -T optframework   # Paket existiert nicht
```

Im Root liegt weder `pyproject.toml` noch `setup.py` noch `setup.cfg` — jedes
Paket hat sein eigenes. Und `optframework` wurde beim Umbau auf den
Monorepo-Zuschnitt (`dpbe`, `qmom`, `mcpbe`, `lmc`, `pbe-core`,
`pbe-optimizer`, …) aufgelöst.

Ausgelöst wird der Workflow nur auf `main`/`master`, deshalb fällt es auf
`dev_eric` nicht auf.

### Warum ist es ein Problem

Die verlinkte Doku unter `pdhs-group.com/PSD_opt/` (Verweis am Ende der
Root-README) kann nicht mehr aktualisiert werden. Wenn dein Betreuer dort
nachschaut, sieht er den Stand vor dem Umbau. Ein rotes CI-Kreuz auf `main` ist
außerdem kein guter erster Eindruck für eine Abgabe.

### Warum ich es trotzdem nicht angefasst habe

Der Workflow gehört zur Gruppen-Infrastruktur, nicht zu deinem Beitrag — und
ihn zu reparieren heißt zu entscheiden, welche Pakete überhaupt in die
API-Doku sollen. Das ist deine bzw. die Entscheidung deines Betreuers.

### Wie könnte man das Problem lösen

Drei Wege, je nachdem wie viel dir daran liegt:

1. **Deaktivieren.** `on:`-Trigger auf `workflow_dispatch` reduzieren. Ehrlicher
   als ein dauerhaft rotes CI, kostet fünf Minuten.
2. **Auf die neue Struktur ziehen.** `sphinx-apidoc` je Paket aufrufen
   (`mcpbe/src/wmcpbe`, `dpbe/src/dpbe`, …), `pip install -e .` durch die
   einzelnen Paketpfade ersetzen. Halber Tag, weil `docs/index.md` und die
   `overview/`-Seiten inhaltlich nachziehen müssen (siehe [D-08](#d-08)).
3. **Liegen lassen** und im Befund dokumentieren, dass es bekannt ist.

## D-10 🟡 31 Löschungen hängen ungestaged im Index

### Was ist das Problem

`git status` zeigt 31 Dateien als ` D` — auf der Platte weg, im Index noch da.
Im Wesentlichen drei Gruppen:

- 17 × `Trials/Results/liquid_*.txt` (Debug-Ausgaben)
- die nach `docs/historical/` verschobenen Markdown-Dateien (aus `docs/`,
  `docs/old/`, `src/wmcpbe/docs/`)
- `Trials/test_kernel_framework.py`, `kernels/agglomeration_acceptance/README.md`

### Warum ist es ein Problem

Du hattest gesagt, alles noch Offene solle von Git ignoriert werden. Bei
Löschungen geht das prinzipiell nicht: `.gitignore` wirkt nur auf **untracked**
Dateien. Eine bereits getrackte Datei bleibt im Repo, bis die Löschung
committet wird — der nächste Clone bekommt sie wieder.

Bei den verschobenen Docs kommt dazu: Git erkennt Verschiebungen erst, wenn
Löschung **und** Neuanlage zusammen gestaged sind. Committest du nur das eine,
sieht die Historie wie „gelöscht und neu erfunden" aus statt wie „verschoben".

### Wie könnte man das Problem lösen

Ein Commit, der beides zusammen aufnimmt:

```bash
git add -A mcpbe/docs mcpbe/src/wmcpbe/docs mcpbe/src/wmcpbe/Trials/Results
```

Danach zeigt `git status` die Docs als `R` (renamed) statt als `D` + `??`.
Wenn du willst, mache ich das am Ende des Durchgangs zusammen mit den
Doku-Änderungen — sag mir nur, ob du einen Commit oder mehrere getrennte willst.

## D-11 🟡 Erledigte Wegwerf-Skripte sind getrackt

### Was ist das Problem

Im Repo-Root liegen drei Dateien, die ihren Zweck erfüllt haben:

- **`CLEANUP_INSTRUCTIONS.md`** — Anleitung zum Löschen von Pfaden, die es nicht
  mehr gibt. Der letzte Schritt der Anleitung lautet, die Anleitung zu löschen.
- **`check_legacy_refs.py`** — prüft fünf Dateien auf Legacy-Begriffe, darunter
  `mcpbe_compression.py`, die im Refactoring entfernt wurde. Das Skript meldet
  dafür stumpf `FILE NOT FOUND`.
- **`analyze_performance.py`** — rechnet mit hartcodierten Zahlen aus einem
  einzelnen Testlauf (`n_particles = 1000`, `q0_end = 265`, Kommentar
  „Tatsächliche Daten aus dem Test"). Kein Argument, keine Eingabe.

Dazu die Suchskripte `search_jit.py`, `search_nucleation.py`,
`search_prepare_break.py`, `run_search.py`, `run_jit_search.py`.

### Warum ist es ein Problem

Sie stehen im Root, also genau dort, wo jemand nach den Einstiegspunkten sucht.
`check_legacy_refs.py` ist zusätzlich irreführend, weil es Ergebnisse liefert,
die auf einer veralteten Dateiliste beruhen.

## D-16 🔵 Zwei Schichten, die dasselbe tun

### Was ist das Problem

`mcpbe_time_helper.py` hat neun freie Funktionen und darunter neun

2. **Wrapper auflösen**, wo sie nur durchreichen — die Aufrufer rufen dann direkt

   sich die Trennung von selbst.

## D-17 🔴 `validate_mass_conservation` meldet einen Massenverlust, den es nicht gibt

### Was ist das Problem

Die Funktion vergleicht zwei Massen, die auf **verschiedene Weise** berechnet
werden:

```python
# Endmasse: korrekt, mit Porositätsfaktor
V_solid[valid_mask] = V_dry[valid_mask] * (1.0 - porosity[valid_mask])
final_solid_mass = float(np.sum(W * V_solid)) * rho_solid

# Referenzmasse: OHNE Porositätsfaktor
V0_dry = solver.V0[-1, :]                       # das ist V_dry, nicht V_solid
initial_mass = float(np.sum(W0 * V0_dry)) * rho_solid
```

Gemessen an einem Solver, an dem **kein einziger Zeitschritt** gelaufen ist:

```
Startporosität 0.8, 100 Partikel, kein solve()
  passed         : False
  initial_mass   : 1.308997e-06 kg
  final_mass     : 2.617994e-07 kg
  relative_error : 0.8000        <- exakt die Porosität
```

### Warum ist es ein Problem

Die Funktion heißt „validate mass conservation" und meldet bei jeder porösen
Ausgangsware einen Fehler in Höhe der Startporosität — bei der
Referenzkonfiguration mit 80 % Porosität also einen scheinbaren Verlust von
80 %. Wer ihr glaubt, sucht einen Bug, den es nicht gibt. Wer ihr nicht
glaubt, hat keine Massenprüfung mehr.

Der Pfad wird nur betreten, wenn `initial_solid_mass` **nicht** übergeben
wird. Mit explizit übergebener Referenzmasse rechnet die Funktion korrekt.

### Wie könnte man das Problem lösen

`solver.V0[0]` ist bereits die Feststoffzeile, und `solver.porosity0` hält die
Startporosität — beides ist da, es wird nur nicht benutzt. Zwei Varianten:

```python
# a) über die gespeicherte Startporosität, symmetrisch zur Endmasse
poro0 = solver.porosity0
V0_solid = np.where(np.isnan(poro0), solver.V0[-1, :], solver.V0[-1, :] * (1.0 - poro0))

# b) direkt die Feststoffzeile - setzt voraus, dass sie gefüllt ist (siehe D-19)
V0_solid = solver.V0[:solver.dim, :].sum(axis=0)
```

Ich würde (a) nehmen: sie ist exakt spiegelbildlich zur Endmasse-Berechnung
und damit unabhängig von D-19.

### Entscheidung (21.08.2026)

**Erledigt sich durch D-19**: `helpers.py` wurde komplett gelöscht (siehe dort).
Lösung (a) war damit nicht mehr zu testen — es gibt keine Funktion mehr, die
sie brauchen könnte.

## D-19 🟠 `setup_initial_particles` lässt die Feststoffzeile auf Null

### Was ist das Problem

`V_flat` hat `dim+1` Zeilen: die ersten `dim` halten das Feststoffvolumen je
Komponente, die letzte das Trockenvolumen. `_initialize_particles` dokumentiert
das ausdrücklich („Row 0: Solid volume").

`setup_initial_particles` füllt Zeile 0 aber nur im Mehrkomponentenfall:

```python
V_flat = np.zeros((solver.dim + 1, n_particles), dtype=float)
V_flat[-1, :] = v_particle          # V_dry
if solver.dim > 1:                  # <- bei dim == 1 uebersprungen
    for i in range(solver.dim):
        V_flat[i, :] = v_particle / solver.dim
```

Bei `dim == 1` — dem Standardfall — bleibt Zeile 0 also auf `0.0`.
`framework/builder.py` macht es an derselben Stelle richtig:

```python
V_flat[0, :] = particle_volume * (1.0 - float(p["initial_porosity"]))
```

### Warum ist es ein Problem

`calc_moments_over_time` liest bei `dim == 1` genau diese Zeile 0. Gemessen:

```
nach setup_initial_particles (dim=1, Porositaet 0.5):
  V_flat[0,:5]  = [0. 0. 0. 0. 0.]
  V_flat[-1,:5] = [5.236e-13 ...]
  korrekt waere  V_dry*(1-0.5) = 2.618e-13

  mu[1,0,:] ueber die Zeit: [0. 0.]   -> identisch Null
```

Die Momentenauswertung liefert also durchgehend Null.

**Einordnung:** aktuell wirkungslos, weil `setup_initial_particles` von keinem
Skript im Repo mehr aufgerufen wird — nur `helpers.py` selbst und ein
Doc-Querverweis in `mcpbe_base.py` nennen sie. Der Solver selbst rechnet
außerdem fast überall mit der abgeleiteten Form `V_dry * (1 - ε)`
(`get_V_solid`, `_merge_pair`), nicht mit Zeile 0. Es ist eine gestellte Falle,
kein aktiver Fehler.

### Wie könnte man das Problem lösen

Eine Zeile, analog zu `builder.py`:

```python
if np.isnan(initial_porosity):
    V_flat[0, :] = v_particle
else:
    V_flat[0, :] = v_particle * (1.0 - initial_porosity)
```

Alternativ die Funktion löschen, wenn sie niemand mehr braucht — dann fällt
auch D-17 zur Hälfte weg.

### Was ist das Problem

merkt man es nicht, weil nichts im Normalpfad `lmc_adapter` importiert; wer

Module einliest (Sphinx-autodoc, `pytest --collect`), bekommt einen Fehler ohne
erkennbaren Zusammenhang.

Entweder `lmc` und die ML-Pakete als optionale Abhängigkeiten in
`pyproject.toml` deklarieren (Poetry: `[tool.poetry.extras]`), oder den Import
absichern und beim tatsächlichen Gebrauch mit klarer Meldung scheitern:

```python
try:

except ImportError as exc:
    raise ImportError(
        "The LMC fragment sampler requires the 'lmc' package. "
        "Install it from the repo: pip install -e lmc/"
    ) from exc
```

ausgewertet wurde — `LMCFlowAdapter` und ihre drei verschachtelten
`torch.nn.Module`-Unterklassen (`_CondMLP`, `_RealNVPCoupling`,
`_CondRealNVP`) wurden bedingungslos auf Modulebene definiert und stürzten
beim Import ohne `torch` mit `NameError` ab — der Guard war nutzlos. Behoben
durch eine bedingte Basisklasse (`_TorchModule = torch.nn.Module if
_TORCH_OK else object`).

**Verifiziert** durch echte Simulation der fehlenden Pakete

## D-23 🔵 Konsolenausgaben deutsch, Code englisch

### Was ist das Problem

`framework/run_reference_repeats.py` gibt seinen Fortschrittsbericht auf
Deutsch aus (`"Seeds wirken:"`, `"Konvergenz n_phys:"`, `"Der Standardfehler
faellt nicht wie 1/sqrt(N)"`). Docstrings und Kommentare derselben Datei sind
jetzt englisch.

### Warum ist es ein Problem

Streng genommen kein Bruch: Konsolenausgabe ist Bedienoberfläche, nicht
Dokumentation. Aber es ist auffällig, wenn dein Betreuer das Skript startet.

In `framework/runner.py` und `statistics.py` habe ich die Ausgaben mit
übersetzt, weil sie dort Fehler- und Statusmeldungen einer Bibliothek sind —
in `run_reference_repeats.py` ist es dein Arbeitsbericht.

### Wie könnte man das Problem lösen

Entweder mitübersetzen (dann ist alles englisch), oder bewusst so lassen und
den Grund im Modul-Docstring festhalten — das habe ich vorläufig getan:

    Console output of this script is German by design -- it is a working tool,
    not documentation.

Sag Bescheid, wenn du es anders willst.
