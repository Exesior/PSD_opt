# WMCPBE Projekt - Detaillierte Architekturbeschreibung für Refactoring

## 1. Physikalischer Hintergrund

Das Projekt simuliert eine **Nassgranulation mittels Monte-Carlo-Simulation** (Weighted DSMC - Direct Simulation Monte Carlo). 

### Prozessbeschreibung:
1. **Ausgangszustand**: Monodisperse Pulverpartikel in einem Hochleistungsmischer
2. **Flüssigkeitszugabe**: Flüssigkeit wird in den Mischer gesprüht (Droplet-Größe ~1µm)
3. **Agglomeration**: Durch Flüssigkeitsbrücken beginnen Partikel zu agglomerieren
4. **Ziel**: Berechnung der Partikelgrößenverteilung (PSD - Particle Size Distribution) am Ende des Prozesses

### Wichtige physikalische Konzepte:

#### Computational Weight (W) - ZENTRALES KONZEPT:
- Jedes computational particle repräsentiert W physical particles
- Formel: `W = N_physical / N_computational`
- Hohes W = viele physikalische Partikel werden durch ein simulationspartikel repräsentiert
- W ändert sich während der Simulation (Agglomeration erhöht W, Breakage verringert W)

**KRITISCHE UNTERSCHEIDUNG: n_phys vs n_comp**
```
n_comp (computational particles):
  - Anzahl der Partikel im Simulator (Array-Länge a_tot)
  - Typisch: 500 - 4000 Partikel (für Performance)
  - Wird durch Rekonstruktion kontrolliert (recon_N_max)

n_phys (physical particles):
  - Tatsächliche Anzahl realer Partikel im Experiment
  - Typisch: 10^6 - 10^12 Partikel
  - Berechnet aus: n_phys = Sum(W_i) für alle computational particles i

Beispiel:
  n_comp = 1000 computational particles
  W = [10, 20, 15, ..., 25] (variiert pro Partikel)
  n_phys = Sum(W) = 1.5 × 10^7 physical particles
  
  Ein computational particle mit W=50 repräsentiert
  50 identische physikalische Partikel!
```

#### Partikelintensiv vs. Partikelextensiv - SPEICHERUNG DER EIGENSCHAFTEN:

**WICHTIG FÜR REFACTORING:** Alle Partikeleigenschaften werden **PARTIKELINTENSIV** gespeichert!

Das bedeutet: Eigenschaften gelten PRO PHYSIKALISCHEM PARTIKEL (n_phys), nicht pro computational particle!

```python
# Intensive Eigenschaften (pro physical particle):
V_flat[i]           # Volumen EINZELNES physical particle [m³]
liquid_volume[i]    # Flüssigkeit EINZELNES physical particle [m³]
porosity[i]         # Porosität EINZELNES physical particle (dimensionslos)
saturation[i]       # Sättigung EINZELNES physical particle (0-1)
X[i]                # Durchmesser EINZELNES physical particle [m]

# Extensive Eigenschaften (skalieren mit W):
# Werden NICHT direkt gespeichert, sondern berechnet:
V_total_particle_i = W[i] * V_flat[i]     # Gesamtvolumen aller repräsentierten Partikel
liquid_total_i = W[i] * liquid_volume[i]  # Gesamtflüssigkeit aller repräsentierten Partikel
```

**Warum ist das wichtig?**

1. **Bei Vc-Verdopplung (DSMC):**
   ```python
   # W wird verdoppelt (mehr physical particles repräsentiert)
   W_new = np.concatenate((W_active, W_active))  # W × 2
   
   # ABER: Intensive properties bleiben GLEICH!
   # Denn jedes physical particle hat immer noch dieselben Eigenschaften
   liquid_volume[:old_a] = lv_active
   liquid_volume[old_a:a_tot] = lv_active  # KOPIEREN, nicht skalieren!
   porosity[:old_a] = por_active
   porosity[old_a:a_tot] = por_active      # KOPIEREN, nicht skalieren!
   ```

2. **Bei Agglomeration:**
   ```python
   # Zwei computational particles i, j agglomerieren
   # Jeder repräsentiert W[i] bzw. W[j] physical particles
   
   # Child bekommt intensive properties der Eltern (gewichteter Durchschnitt)
   # liquid_volume[child] = (W[i]*liq[i] + W[j]*liq[j]) / (W[i] + W[j])
   # POROSITÄT wird über Kernel berechnet (nicht einfach mitteln!)
   
   # W[child] = dW (neues Gewicht für merged particles)
   ```

3. **Bei Breakage:**
   ```python
   # Parent bricht in Fragmente
   # liquid_volume wird proportional zu Volumen verteilt
   # liquid_volume[frag_k] = liquid_volume[parent] × (V_frag_k / V_parent)
   # Denn: Flüssigkeit pro physical particle skaliert mit Partikelgröße
   ```

**Häufige Fehlerquelle beim Refactoring:**
```python
# ❌ FALSCH: liquid_volume mit W skalieren
liquid_volume[i] *= W[i]  # NEIN! liquid_volume ist bereits pro physical particle!

# ✅ RICHTIG: liquid_volume bleibt unverändert bei W-Änderung
# Nur bei Ereignissen (Agg/Break/Nuc) ändern sich intensive properties
```

#### Control Volume (Vc):
- DSMC hält Partikeldichte konstant: `Sum(W) / Vc = constant`
- Bei Agglomeration: Partikelanzahl ↓ → Vc wird verdoppelt → Partikel werden dupliziert
- Wichtig für korrekte physikalische Skalierung der Ereignisse

#### Volumen-Semantik (kritisch für Massenerhaltung):
- `V_flat[:dim]` = V_solid (Feststoffvolumen OHNE Poren)
- `V_flat[-1]` = V_dry (Gesamtvolumen MIT Poren)
- Für poröse Partikel: `V_dry = V_solid / (1 - porosity)`
- Für Vollkörper (keine Porosität): `V_dry = V_solid`

## 2. Software-Architektur

### 2.1 Hauptklassen-Hierarchie

```
MCPBESolver (Hauptsolver)
├── MCPBEBase (Basis-Klasse via Mehrfachvererbung)
│   ├── Partikelzustand (V_flat, W, X, liquid_volume, porosity, saturation)
│   ├── Control Volume Management
│   ├── Hauptsolve-Loop mit Event-driven Time Stepping
│   └── KernelManager Integration
├── MCPBEAgg (Agglomeration-Mixin)
│   ├── Beta-Kernel-Berechnung (Partikelkollisionsrate)
│   ├── Partner-Selection (Fenwick Sampler)
│   └── Agglomerations-Event-Durchführung
├── MCPBEBreak (Breakage-Mixin)
│   ├── Breakage-Rate-Berechnung (MLP/JIT/Kernel)
│   ├── Fragment-Verteilung (CDF-Tabellen, LMC-Adapter)
│   └── Multi-Fragment-Event-Durchführung
├── MCPBEPost (Post-Processing-Mixin)
│   ├── Momentenberechnung (µ(i,j,t))
│   └── PSD-CDF-Berechnung über Zeit
├── ReconstructionMixin (Rekonstruktion/Resampling)
│   ├── CAM (Cell Average Method)
│   ├── RS (Resampling mit C-1 Korrektur)
│   ├── 2PM (Two-Point-Methode)
│   └── QMX (Quantile MiX - hybride Methode)
└── Handler (Komposition, keine Vererbung)
    ├── NucleationHandler (Flüssigkeitszugabe)
    ├── CompressionHandler (Porositätskompression, legacy)
    └── ContinuousProcessesHandler (Kontinuierliche Prozesse)
```

### 2.2 Method Resolution Order (MRO)

```python
MCPBESolver → MCPBEPost → MCPBEBreak → MCPBEAgg → MCPBEBase → ReconstructionMixin
```

**Warum diese Reihenfolge?**
- Post-Processing muss zuletzt kommen für Zugriff auf alle States
- Breakage vor Agglomeration für korrekte Event-Reihenfolge im Mix-Modus
- Base enthält fundamentale Initialisierung

## 4. Kernkomponenten im Detail

### 4.1 MCPBEBase - Core Solver

**Verantwortlichkeiten:**
- Partikelarrays verwalten: `V_flat`, `W`, `X`, `liquid_volume`, `porosity`, `saturation`
- Control Volume Management mit dynamischem Verdoppeln
- Hauptsolve-Loop mit Event-driven Time Stepping
- Capacity Management für Partikelarrays (dynamisches Wachstum)
- KernelManager initialisieren

**Wichtige Methoden:**
```python
_initialize_particles()     # Initialisiert Partikel aus Verteilung oder CDF
_initialize_samplers()      # Baut FenwickSampler für Agg/Break
_maybe_double_control_volume()  # DSMC: Vc verdoppeln wenn Partikel < 50%
_ensure_capacity_for()      # Dynamisches Array-Wachstum
```

**State Arrays (alle Länge = _cap):**
- `V_flat[dim+1, _cap]`: Volumina (dim Komponenten + total)
- `W[_cap]`: Computational Weights
- `X[_cap]`: Partikeldurchmesser (aus V_total berechnet)
- `liquid_volume[_cap]`: Flüssigkeitsvolumen pro Partikel [m³]
- `porosity[_cap]`: Porosität (NaN für Vollkörper)
- `saturation[_cap]`: Sättigung (0-1, nur für poröse Partikel)

### 4.2 MCPBEAgg - Agglomeration

**Physikalisches Modell:**
- Partikel kollidieren mit Rate β(i,j) abhängig von Radien r_i, r_j
- Kollisionseffizienz α(i,j) für 2D-Systeme (4 Komponentenkombinationen)
- Effektive Rate: `β_eff = β × α`

**Algorithmus:**
1. Wähle Partikel i proportional zu Propensität r_i = Σⱼ Wⱼ×β(i,j)
2. Wähle Partner j proportional zu Wⱼ (gewichtetes Sampling)
3. Berechne β(i,j) via Kernel
4. Akzeptanzprüfung (SIZEEVAL, Stokes-Kriterium via Kernel)
5. Erzeuge neues Partikel mit dW Gewicht
6. Reduziere Eltern-Gewichte um dW
7. Rebuild Propensities (O(n²) via JIT oder Kernel)

**Wichtige Methoden:**
```python
_beta(i, j)                    # Berechnet β(i,j) via Kernel
_rebuild_all_propensities()    # Neuberechne alle r_i (parallel via JIT)
_do_one_agg()                  # Führt ein Agglomerationsereignis durch
_pick_partner_kernel()         # Wählt Partner j gewichtet nach W
```

**JIT-optimierte Kernel:**
- `rebuild_r_array_shear()`: Scherungsgetriebene Agglomeration
- `rebuild_r_array_brownian()`: Brownsche Bewegung
- `rebuild_r_array_constant()`: Konstanter Kernel
- `rebuild_r_array_sum()`: Summenkernel

### 4.3 MCPBEBreak - Breakage

**Physikalisches Modell:**
- Breakage-Rate S(V) abhängig von Partikelvolumen
- Fragmentverteilung aus CDF-Tabellen oder LMC (Lattice Monte Carlo)

**Fragmentverteilungs-Methoden:**
1. **Precomputed Tables**: Tabelle/Rank/Copula/Flow-Adapter
2. **Live LMC**: Echtzeit-Fragmentgenerierung
3. **Analytisch**: Stepwise Splitting aus Beta-Funktion

**Algorithmus:**
1. Wähle Partikel k proportional zu Propensität W_k × S_k
2. Bestimme Fragmentanzahl n (stochastisches Runden von E[n])
3. Generiere n Fragmente via CDF-Sampling
4. Erzeuge neue Partikel für Fragmente (jeweils Gewicht dW)
5. Reduziere Elterngewicht um dW
6. Update Breakage/Agg Samplers

**Wichtige Methoden:**
```python
_calc_break_rates_full()       # Berechnet alle Breakage-Raten
_break_rate_single(i)          # Einzelne Breakage-Rate
_build_break_function()        # Baut CDF-Tabellen für Fragmente
_produce_one_frag_from_remaining()  # Sampling eines Fragments
_do_one_break()                # Führt ein Breakage-Ereignis durch
```

**LMC-Adapter:**
- `LMCTableAdapter`: Marginaltabellen
- `LMCRankAdapter`: Rank-basierte Tabellen
- `LMCCopulaAdapter`: Copula-basierte Korrelationen
- `LMCFlowAdapter`: Flow-basierte Modelle
- `LMCLiveAdapter`: Live-LMC-Simulator

### 4.4 NucleationHandler - Flüssigkeitszugabe

**Physikalisches Modell:**
- Flüssigkeit wird als diskrete Tropfen (Droplets) zugegeben
- Alle Partikel haben gleiche Kollisionswahrscheinlichkeit (uniform sampling by weight W)
- DSMC-Skalierung: `physical_droplets = (Vc_ref / Vc) × W_selected`

**Duration-Spezifikation (mutually exclusive):**
- **Option A**: Direkte Duration via `liquid_addition_duration` [s]
- **Option B**: Berechnet aus `target_wt_percent + solid_mass_in_mixer + densities`
  - Formel: `duration = (solid_mass × wt%/100 / rho_liquid) / flow_rate`

**DSMC-Skalierung (kritisch!):**
```
Computational Weight (W):
  W = N_physical / N_computational
  Beispiel: W=50 bedeutet 50 physikalische Partikel pro computational particle

Droplet distribution:
  droplet_comp = 1 (ein computational event)
  droplet_phys = (Vc_ref / Vc) × W_selected
  
Beispiel: Vc_ref=1e-6 m³, Vc=2e-6 m³, W=50
  → Physical droplets = (1e-6/2e-6) × 50 = 25 droplets
```

**Wichtige Methoden:**
```python
step(current_time, dt_event)        # Ein Nucleation-Schritt
_distribute_liquid_volume()         # Verteilt Flüssigkeit als Droplets
_select_particle_uniform_physical() # Wählt Partikel uniform nach phys. Count
_ensure_samplers()                  # Baut FenwickSampler für W-gewichtetes Sampling
```

**Statistiken:**
- `_droplets_added_total`: Gesamte physikalische Droplets (weighted sum)
- `_liquid_volume_added_total`: Gesamtes Flüssigkeitsvolumen [m³]
- `_liquid_remainder`: Akkumulierter Rest für nächste Iteration (Massenerhaltung!)

### 4.5 ContinuousProcessesHandler - Kontinuierliche Prozesse

**Prozesse:**
1. **Liquid Internalization** (Braumann et al. 2007):
   - Kapillar-getriebenes Eindringen von Flüssigkeit in Poren
   - Gleichung: `dl_intern/dt = k × l_ex × (v_pore - l_intern)`
   
2. **Porosity Compression**:
   - Exponentieller Porositätszerfall unter Scherkräften
   - Gleichung: `ε(t) = ε_min + (ε_0 - ε_min) × exp(-rate × t)`

**Prozessreihenfolge pro Zeitschritt:**
1. Liquid Internalization updaten (Sättigung ändern)
2. Porosity Compression anwenden (Porenvolumen reduzieren)
3. Überschüssige Flüssigkeit externalisieren wenn S > 1

**Wichtige Methoden:**
```python
step(current_time, dt_event)     # Ein Schritt kontinuierlicher Prozesse
_apply_internalization(dt)       # Wendet Internalisierung an
_apply_compression(dt)           # Wendet Kompression an
```

### 4.6 ReconstructionMixin - Rekonstruktion/Resampling

**Zweck:**
- Reduziere Partikelanzahl wenn zu groß (> recon_N_max)
- Erhalte statistische Momente (M0, M1, M2)
- Vermeide numerische Diffusion der PSD

**Methoden:**

#### CAM (Cell Average Method):
- Baue Grid in Komponenten-Volumenraum
- Berechne Mittelwert pro Zelle (gewichtet nach W)
- Verteile Zellmasse auf benachbarte Pivot-Punkte (linear/bilinear)

#### RS (Resampling mit C-1 Korrektur):
- Bucket Partikel nach CAM-Zellen
- Resample pro Zelle nach M0-Proportion
- Two-weight correction für M1-Erhaltung (1D/2D)

#### 2PM (Two-Point-Methode):
- Pro Zelle: zwei Repräsentanten bei x₁ = mean - σ, x₂ = mean + σ
- Gewichte w₁ = w₂ = M0/2
- Erhält M0, M1, M2 exakt

#### QMX (Quantile MiX - hybrid):
- Partitioniere Partikel nach Vtot-Quantilen (small/mid/tail)
- Wende unterschiedliche Methoden pro Partition an:
  - Small: 2PM (gut für kleine Partikel)
  - Mid: RS (effizient, gute Genauigkeit)
  - Tail: CAM (erhält Tail-Struktur)

**Wichtige Methoden:**
```python
maybe_reconstruct(iter_count)    # Prüft ob Rekonstruktion nötig
reconstruct(method="CAM")        # Führt Rekonstruktion durch
_kernel_cam()/RS()/2pm()/qmx()   # Kernel-spezifische Logik
```

## 6. FenwickSampler - Effizientes gewichtetes Sampling

**Zweck:**
- O(log n) Sampling nach Gewichten W
- O(log n) Updates bei Gewichtsänderung
- Kritisch für Performance bei vielen Partikeln (>10.000)

**API:**
```python
sampler = FenwickSampler(weights)
idx = sampler.sample(rng)           # Sample Index nach weights
sampler.update(idx, new_weight)     # Update einzelnes Gewicht O(log n)
sampler.append(weight)              # Neues Element hinzufügen
sampler.remove(idx)                 # Element entfernen (swap-with-last)
total = sampler.total()             # Summe aller Gewichte
```

**Implementierung:**
- Binary Indexed Tree (Fenwick Tree)
- Numba-JIT für Performance
- Prefix-Sum-Suche für Sampling

## 7. Wichtige physikalische Invarianten

### 7.1 Massenerhaltung

**Bei Agglomeration:**
```python
# V_flat[:dim] = V_solid (CONSTANT!)
V_solid_merged = V_solid_i + V_solid_j  # Masse erhalten!

# V_flat[-1] = V_dry (ändert sich mit Porosität)
V_dry_merged = V_solid_merged / (1 - porosity_merged)
```

**Bei Breakage:**
```python
# Fragment-Volumina summieren zu Parent-Volumen
sum(V_frag) = V_parent

# liquid_volume wird proportional verteilt
liquid_frag = liquid_parent × (V_frag / V_parent)
```

**Bei Nucleation:**
```python
# Total liquid added = flow_rate × duration
# Keine systematischen Verluste durch _liquid_remainder
```

### 7.2 Intensive vs. extensive Eigenschaften

Siehe auch **Abschnitt 1: Partikelintensiv vs. Partikelextensiv** für detaillierte Erklärung.

**Kurzfassung:**

| Eigenschaft | Typ | Verhalten bei Vc-Verdopplung |
|-------------|-----|------------------------------|
| `W` | Extensiv | Wird verdoppelt (×2) |
| `V_flat` | Intensiv | Bleibt gleich (pro physical particle) |
| `liquid_volume` | Intensiv | Bleibt gleich (pro physical particle) |
| `porosity` | Intensiv | Bleibt gleich |
| `saturation` | Intensiv | Bleibt gleich |
| `X` | Intensiv | Bleibt gleich |

**Vc-Verdopplung Code:**
```python
# W wird verdoppelt (repräsentiert mehr physical particles)
W_new = np.concatenate((W_active, W_active))

# Intensive properties werden KOPIERT (nicht skaliert!)
liquid_volume[:old_a] = lv_active
liquid_volume[old_a:a_tot] = lv_active  # Gleiche Werte!
```

## 8. Refactoring-Anforderungen

### 8.1 Plausibilitätsprüfung

Beim Refactoring MUSS folgende Plausibilitätsprüfung implementiert werden:

**Vor jeder Änderung:**
1. **Massenerhaltung prüfen:**
   - `sum(W × V_solid)` vor/nach Operation vergleichen
   - Toleranz: < 0.1% relative Abweichung
   
2. **Liquid Conservation prüfen:**
   - `sum(W × liquid_volume)` vor/nach Operation
   - Besonders kritisch bei Nucleation und Breakage

3. **Bounds-Checks:**
   - `W > 0` für alle aktiven Partikel
   - `0 <= porosity < 1` (oder NaN für Vollkörper)
   - `0 <= saturation <= 1` (für poröse Partikel)
   - `V_flat > 0` für alle Volumina

4. **DSMC-Invarianten:**
   - `Sum(W) / Vc ≈ constant` (Partikeldichte erhalten)
   - Nach Vc-Verdopplung: `Sum(W)_new ≈ 2 × Sum(W)_old`

**Nach jeder Änderung:**
1. **Array-Konsistenz:**
   - Alle Arrays gleiche Länge (_cap)
   - `a_tot <= _cap`
   - Indizes im gültigen Bereich

2. **Sampler-Konsistenz:**
   - `FenwickSampler.total() ≈ sum(W[:a_tot])`
   - Alle Gewichte nicht-negativ

3. **Zeitentwicklung:**
   - `t_vec` monoton steigend
   - `dt_event > 0` für alle Events

### 8.2 Dokumentation der Änderungen

Jede Änderung MUSS dokumentiert werden mit:

1. **Betroffene Dateien:**
   ```markdown
   - wmcpbe/mcpbe_agg.py: Zeilen 150-200
   - wmcpbe/kernel_integration.py: Zeilen 50-75
   ```

2. **Art der Änderung:**
   - [ ] Bugfix
   - [ ] Performance-Optimierung
   - [ ] Neue Feature
   - [ ] Refactoring (ohne Funktionsänderung)
   - [ ] Dokumentation

3. **Physikalische Auswirkung:**
   - Welche Gleichung/Formel wurde geändert?
   - Referenz zu Literatur/Quelle

4. **Tests:**
   - [ ] Unit-Tests aktualisiert
   - [ ] Plausibilitätsprüfung bestanden
   - [ ] Vergleich mit Referenzsimulation

5. **Versionierung:**
   - Commit-Message im Format: `[TYPE] kurze Beschreibung`
   - Beispiel: `[REFACTOR] MCPBEAgg: Beta-Berechnung auf Kernel delegieren`

## 9. Bekannte Probleme und technische Schulden

### 9.1 Inkonsistente Volumen-Semantik

**Problem:**
- Legacy-Code behandelt `V_flat[:dim]` teilweise als V_dry, teilweise als V_solid
- Führt zu Massenerhaltungsproblemen bei porösen Partikeln

**Lösung im Refactoring:**
- Explizite Benennung: `V_solid` vs `V_dry`
- Helper-Methoden: `get_V_solid(i)`, `get_V_dry(i)`
- Strikte Validierung bei Initialisierung

### 9.2 Performance-Engpässe

**Kritische Stellen:**
1. `_rebuild_all_propensities()`: O(n²) für große Partikelanzahlen
   - Lösung: Kernel-basierte JIT-Batch-Funktionen nutzen
   
2. `_pick_partner_kernel()`: Python-Loop für nicht-standard Kernel
   - Lösung: Numba-JIT auch für custom Kernel

3. FenwickSampler-Updates bei jedem Event
   - Lösung: Incremental updates (_pending_weight_updates)

### 9.3 Testabdeckung

**Fehlende Tests:**
- Nucleation mit variabler Vc
- Breakage mit LMC-Adaptern
- Rekonstruktion (CAM/RS/QMX) Grenzfälle
- Continuous Processes mit allen Kerneln

# tests/test_plausibility.py
import numpy as np

def test_mass_conservation_after_agglomeration(solver_1d):
    """Prüfe Massenerhaltung nach Agglomerations-Event."""
    # Initial state
    V_solid_before = np.sum(solver_1d.W[:solver_1d.a_tot] * 
                            solver_1d.V_flat[0, :solver_1d.a_tot])
    
    # Execute one agglomeration event
    solver_1d._do_one_agg()
    
    # Final state
    V_solid_after = np.sum(solver_1d.W[:solver_1d.a_tot] * 
                           solver_1d.V_flat[0, :solver_1d.a_tot])
    
    # Check conservation (tolerance 0.1%)
    rel_diff = abs(V_solid_after - V_solid_before) / V_solid_before
    assert rel_diff < 0.001, f"Mass not conserved: {rel_diff*100:.3f}% change"

def test_weights_positive(solver_1d):
    """Alle Gewichte müssen positiv sein."""
    assert np.all(solver_1d.W[:solver_1d.a_tot] > 0), "Negative weights found"

def test_porosity_bounds(solver_1d):
    """Porosität muss in [0, 1) oder NaN sein."""
    poro = solver_1d.porosity[:solver_1d.a_tot]
    valid = np.isnan(poro) | ((poro >= 0) & (poro < 1))
    assert np.all(valid), "Porosity out of bounds"

## 18. Performance-Überlegungen

### 18.1 Kritische Performance-Stellen

| Operation | Komplexität | Optimierung |
|-----------|-------------|-------------|
| `_rebuild_all_propensities()` | O(n²) | JIT-Batch-Funktionen |
| `_pick_partner_kernel()` | O(n) | Fenwick-Sampling O(log n) |
| `_calc_break_rates_full()` | O(n) | Vektorisierung |
| `_ensure_samplers()` | O(n) | Incremental Updates |
| `_distribute_liquid_volume()` | O(droplets) | Batch-Verteilung |

### 18.2 Numba-JIT Optimierung

**Best Practices:**
```python
from numba import njit, prange

# Parallel für große Arrays
@njit(parallel=True, cache=True)
def rebuild_r_array_parallel(W, R, beta_params):
    n = len(W)
    r = np.zeros(n)
    for i in prange(n):  # Parallel loop
        ri = 0.0
        for j in range(n):
            ri += W[j] * compute_beta(R[i], R[j], beta_params)
        r[i] = ri
    return r

# Cache für wiederholte Aufrufe
@njit(cache=True)
def compute_beta(r1, r2, params):
    # Wird beim ersten Aufruf kompiliert, dann gecached
    return params['corr_beta'] * (r1 + r2)**3
```

**Windows-spezifisch:**
- NUMBA_ENABLE_CUDASIM=1 für Testing ohne GPU
- NUMBA_CACHE_DIR=%USERPROFILE%\.numba\cache für Pfadkontrolle

### 18.3 Memory-Optimierung

**SoA (Structure of Arrays) vs AoS (Array of Structures):**

Aktuell (SoA - gut für Vektorisierung):
```python
V_flat[dim+1, _cap]  # Alle Volumina zusammen
W[_cap]              # Alle Gewichte zusammen
X[_cap]              # Alle Durchmesser zusammen
```

Vorteile:
- Bessere Cache-Lokalität
- SIMD-Vektorisierung möglich
- Einfacheres JIT-Compiling

from .base import AggregationKernel

class MyCustomKernel(AggregationKernel):
    name = 'my_custom'
    
    def __init__(self, param_a=1.0, param_b=2.0):
        self.param_a = param_a
        self.param_b = param_b
